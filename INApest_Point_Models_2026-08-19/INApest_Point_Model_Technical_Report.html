1. Purpose and modelling scope

The point-model family was developed for small-area incursion and eradication problems where representing actual occurrence locations is more useful than dividing the landscape into predefined nodes. Every simulated point is exactly one biological entity. Examples include one invasive tree or one yellow-legged hornet (YLH) nest.

The engines borrow the management/environment/information architecture of the INApestMeta family but replace node occupancy and node-to-node movement with explicit coordinates and stochastic spatial kernels. No prior familiarity with INApest is needed to use the functions in this package.

When the point formulation is attractive

  • Incursions occupy a limited spatial extent.
  • Detection/search geometry matters at tens to hundreds of metres.
  • Individual source-to-destination pathways are important.
  • Life-stage transitions can involve physical relocation.
  • Management or habitat varies continuously across space.

What a point is not

A point is not a local population or cell abundance. If one nest produces five established daughter nests, five new rows/points are created. This makes demographic stochasticity and invasion genealogy explicit.

The package contains two serial engines and thin parallel wrappers:

2.1 Point state

Both engines maintain an individual-level table containing coordinates, identity/genealogy and response state. The core fields are id, parent_id, x, y, stage, birth_timestep, have_info, detected, managing and last_known_timestep.

3. INApestMetaPoint(): process semantics

Within each timestep the generic engine executes the following sequence:

  1. Management adoption, natural survival and management mortality. Management adoption requires the point to have information. Natural survival and management mortality then remove individuals.
  2. Propagule production and spread. Surviving points draw Poisson propagule counts from PropaguleProduction, modified by management fecundity reduction where applicable. Each propagule is classified as SDD/LDD, displaced by its kernel, optionally nudged by habitat search, and tested for establishment.
  3. External incursions. Optional new points can be generated by ExternalIncursionGenerator.
  4. Information persistence and transfer. Information can persist at extant points and at known/detected locations, and can transfer by distance or a user-defined information kernel.
  5. Detection. Detection occurs after population dynamics, so newly acquired information affects management from the next timestep.
Nprop,i,t ~ Poisson( λi,t × [1 − Mi,t Fi,t] )

Here M indicates active management and F is realised fecundity reduction. SpreadReduction is separate: it suppresses outgoing propagules after they are produced and can act on LDD only (default) or all spread.

4. INApestPointTransitionMatrix(): stage structure

The stage-structured engine uses the same point representation and management/spatial machinery but interprets a restricted transition matrix. Rows are target stages and columns are source stages.

Allowed matrix structure

target \ sourcestage 1stage 2…stage S
stage 1stasisfecundityfecundityfecundity
stage 2progressionstasis00
…0progression…0
stage S00progressionterminal survival

Important constraints

  • Only diagonal stasis/survival, adjacent sub-diagonal progression and row-1 fecundity entries are allowed.
  • For non-terminal stage s, stasis + progression must be ≤ 1; the remainder is stage-process mortality.
  • Terminal diagonal survival must be ≤ 1.
  • Fecundity can exceed 1 because it is a mean Poisson offspring rate, not a probability.

4.1 Timestep ordering

  1. Management adoption and management mortality.
  2. Fecundity from the surviving pre-transition parents.
  3. Stage survival/stasis/progression; progression may use a transition-specific movement kernel.
  4. Reproductive SDD/LDD and establishment for the already-generated propagules.
  5. External incursions.
  6. Information persistence/transfer.
  7. Detection.

This ordering is important for interpretation: a parent can contribute fecundity in a timestep and then die under the stage transition process later in that same timestep.

4.2 Movement during stage transitions

TransitionKernels is a list of length Nstages - 1; entry s applies when stage s progresses to s+1. A NULL entry means progression in place. This cleanly represents processes such as a primary YLH nest moving a relatively short distance before establishing the main nest.

TransitionHabitatSearch can apply active habitat finding to the relocated destination. By default the transition matrix probability itself is treated as the successful biological transition; ApplyHabitatToTransitions can add an explicit habitat/transition-establishment filter when that is biologically desired.

5. Continuous-space dispersal

There is no node-to-node connectivity matrix. A kernel function returns one dx,dy displacement per propagule. Radial convenience constructors are provided for exponential, lognormal and fixed-distance movement.

x′ = x + Δx     y′ = y + Δy

SDD and LDD remain distinct. In INApestMetaPoint, LDDrate is a scalar probability. In the transition-matrix engine it can also be a timestep vector. Reproductive SDD/LDD kernels in the transition engine may be supplied as one function for all stages or a list of stage-specific functions.

6. Native base-R habitat parameterisation

INApestSpatialGrid() stores a numeric 0–1 matrix plus its rectangular spatial extent. INApestHabitatGrid() is a habitat-specific wrapper using the same representation. Matrix row 1 defaults to the northern/top edge (ymax), with row_origin="ymin" available when needed. NA cells and locations outside the grid are treated as suitability 0.

habitat <- INApestSpatialGrid(
  values = habitat_matrix,
  xmin = 0, xmax = 10000,
  ymin = 0, ymax = 10000
)
P(establishment) = PropaguleEstablishment × EnvEstabProb × H(x,y,t)

6.1 Active habitat finding

Dispersal first generates a provisional destination. If HabitatSearchRadius > 0, the engine examines grid-cell centres within that radius around the provisional destination. It moves only when strictly better habitat exists, selects the maximum available suitability, and resolves ties by shortest movement. The nudge therefore never exceeds the search radius.

6.2 Time-varying surfaces without duplicated grids

INApestSpatialSchedule() associates static grids with timestep ranges. The human-oriented change-point form is:

DetectionSpatial <- INApestSpatialSchedule(
  public_only      = grid_public,
  initial_response = grid_response,
  intensive_search = grid_intensive,
  from = c(1, 5, 9)
)

This means timesteps 1–4, 5–8 and 9 onward respectively. Explicit to= ranges are also accepted. Overlaps and uncovered model timesteps are rejected rather than silently resolved.

7. Management parameterisation

The principal management mechanisms are deliberately separate because they represent different causal actions:

mechanismparameterinterpretation
DetectionDetectionProbProbability an extant point is detected at the end of the timestep.
Management adoptionManageProbProbability an informed point adopts/is subject to management in the current timestep.
MortalityMortalityProbProbability active management kills the point.
Fecundity reductionFecundityReductionProportional reduction in propagule production before dispersal.
Spread reductionSpreadReductionProbability management suppresses produced propagules; applies to LDD by default or all spread.

7.1 Spatial modifiers

Each mechanism can be independently multiplied by a static/scheduled spatial surface: DetectionSpatial, ManageSpatial, MortalitySpatial, FecundityReductionSpatial and SpreadReductionSpatial.

μlocal(x,y,t) = μbaseline(t,stage) × S(x,y,t)

The supplied SD is then applied around this local mean and the realised value is clipped to [0,1]. A spatial multiplier of exactly zero is enforced as exactly zero after the stochastic draw so uncertainty cannot create a management process outside its coverage.

For INApestMetaPoint, most baseline management inputs may be a scalar, a vector of length Ntimesteps, or a function of the current point table/timestep/permutation. In the transition engine, detection and mortality additionally support stage vectors and Nstages × Ntimesteps matrices. FecundityReduction and its SD intentionally retain the same simple contract in both engines: scalar or vector of length Ntimesteps, bounded to [0,1].

8. Information, response and detection

The node-based SEAM concept is replaced by distance-based point information transfer. A known location can continue to exist as an information site after the biological entity has been removed. Extant informed points can also serve as sources.

  • InfoRadius + InfoTransferProb provide a simple distance-threshold mechanism.
  • InfoKernel can return source-target transfer probabilities as a function of distance and state.
  • InfoRetentionProb supports stochastic retention.
  • InfoPersistenceSteps supports programmed persistence.
  • ExternalInfoProb / OngoingExternalInfo provide externally sourced information.

Detection occurs after the population processes. Therefore a point detected in timestep t can influence management from timestep t+1, not retrospectively earlier in the same step.

12. Parallel versions

The parallel functions are thin wrappers rather than copies of the biological code. Each worker executes exactly one serial permutation (Nperm = 1) and the master relabels and combines the outputs. Independent L'Ecuyer-CMRG RNG streams are pre-generated so each permutation has a reproducible stream independent of worker allocation.

On Windows the intended backend is PSOCK. The WebAssembly R runtime used for this development snapshot cannot launch genuine multi-process PSOCK workers, so the included tests/INApestMetaPoint_parallel_tests.R performs the two-worker equality check automatically when run in ordinary/native R with at least two cores.

13. Computational and conceptual limits

  • Scaling: the individual representation is intentionally aimed at small-area incursions. Some operations use direct point-to-point or point-to-cell searches; cost can grow rapidly as the number of points, information sites or candidate habitat cells increases.
  • Habitat search: exact native-grid search is transparent but can be expensive for fine grids and large search radii. Grid resolution should reflect biological and operational resolution rather than GIS source resolution by default.
  • Local capacity: LocalK/KRadius are a point-based local-capacity analogue, not a literal transfer of node carrying capacity. The transition engine can use stage weights.
  • Boundaries: continuous coordinates are unconstrained unless habitat/establishment or other user logic constrains them. Outside a supplied base-R habitat grid, suitability is zero.
  • Transition topology: the transition engine deliberately supports adjacent progression only; skipped stages or arbitrary retrogression require an extension rather than silently interpreting unused matrix entries.
  • Spatial GIS: core operation is native base R. GIS libraries are best used upstream to construct aligned numeric grids. An optional SpatRaster compatibility path remains in the code but was not part of the validated core in this snapshot.
  • Calibration: software/mechanism tests do not substitute for biological parameter estimation, uncertainty analysis or management validation.

14. Recommended modelling workflow

  1. Choose the generic or transition-matrix engine based on whether explicit life-stage dynamics are required.
  2. Define the simulation coordinate system and a biologically meaningful grid resolution.
  3. Validate demographic behaviour without management or habitat complexity.
  4. Validate each dispersal/transition kernel against its intended distance distribution.
  5. Introduce habitat establishment effects, then active habitat search if biologically justified.
  6. Add detection/information and management mechanisms one at a time.
  7. Use INApestSpatialSchedule() for operational periods rather than duplicating grids each timestep.
  8. Run scenario ensembles and inspect both Summary and event-level/genealogical outputs.
  9. Only then enable native parallel execution for large permutation batches, after running the supplied PSOCK check locally.
